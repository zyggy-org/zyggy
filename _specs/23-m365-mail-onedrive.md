## User Story

**As** the owner,
**I want** Zyggy on the Central VM to work with my Digiverse mailbox and drives as a real tool, with nothing ever routed through my laptop — a "Zyggy — morning brief <date>" Draft every morning (new mail summarised, "work in progress" from the files that changed, proposed actions, at most a few in-thread reply Drafts), a one-off backfill of my mailbox and all my OneDrive/SharePoint files into memory as facts, and the same connector in my remote session —
**So that** Zyggy knows and acts on my company's context from the VM alone, and I still review and send every reply myself in Outlook (D1); nothing is ever sent, deleted, moved or written on my behalf.

**As** Central (the machine role),
**I want** an application identity of my own — a private key generated on this VM that never leaves it, a public certificate the owner uploads once from a browser, a Graph token I mint myself whenever I need one, mailbox access scoped in Exchange to the owner's mailbox only and file access granted site by site — handed to the MCP server as a one-hour token per start, with only read tools and the two Draft tools loaded, deny rules repeating the exclusion, capped runs, validated memory lines and a post-run audit of what a run created,
**So that** no laptop, user session, MFA prompt or password change can interrupt me, no tool that can send, delete, move, share or upload exists in any session, a leaked key can reach no mailbox but the owner's and no site but the granted ones, and a failed run leaves nothing half-done.

**As** the owner maintaining the template,
**I want** `.mcp.json`, the wrapper, `graph.sh`, the skills, validators, rules and tests generic in `zyggy-core`, and every Digiverse fact (tenant, client id, mailbox, drive ids, named sites, exclusions, caps, timer) only in my instance,
**So that** a template change reaches Central with a fast-forward pull and another owner can connect their tenant from the same template.

## Behaviors & Conventions

As the previous draft (one credential/one reader/one-shot hand-off; tool set bounded twice; `Mail.ReadWrite` bounding for a model with tools — layer (1) now reads "no send tool, no Entra `Mail.Send`, no `Application Mail.Send` role in Exchange"; honest unattended posture with five attended runs; injection bounding; idempotence by script; caps; facts only; parse and discard; interactive use with the hourly reconnect; logging once per run; data protection per OQ-5 (a); template/instance), plus:

- **No laptop in Central's operation.** Key generation, token minting, every run, rotation and revocation happen on the VM or in a browser; nothing is ever transferred from the laptop to Central except the template/instance commits through GitHub. Override: none.
- **Scope is enforced in the tenant, not by the model.** Exchange RBAC and `Sites.Selected` bound what the identity can reach regardless of the model or a key holder; the tool configuration bounds what the model can *do*; `graph.sh check --other-mailbox`/`--drive` re-proves the first after any tenant change. Override: a new grant = an owner browser step + an `instance.md`/`m365.json` update + a dated 0002 row.
- **Certificate lifecycle.** `graph.sh check` (and every run's pre-flight) warns 30 days before expiry and fails with exit 3 after it; rotation per runbook within that window. Override: `cert.days` at the next rotation.
