## User Story

**As** the owner,
**I want** a "Zyggy — morning brief <date>" Draft waiting in my Digiverse mailbox every morning — the mail I received since the last run summarised with proposed actions, a "work in progress" section naming the files I and my clients changed, and at most a few reply Drafts in the threads Zyggy proposes to answer — and, once, a backfill over my whole mailbox and all my OneDrive/SharePoint files that teaches Zyggy who my clients are, what I work on and how I work,
**So that** Zyggy knows my company's context the way it knows my personal one, and nothing is ever sent, deleted, moved or written on my behalf without my consent.

**As** the owner acting on the brief,
**I want** the brief to **propose** actions with an id — *send* a reply Draft Zyggy wrote, *move* a mail to one of my folders (Archive included), *delete* a mail (to Deleted Items) — and one command on the VM (`m365-approve.sh`) that shows me each pending proposal with the exact recipient, subject and destination and asks me, one by one, to approve or reject it,
**So that** I decide every send, move and delete myself (D6), in a terminal the model cannot type into, and I can still ignore the proposals and act in Outlook as before.

**As** Central (the machine role),
**I want** one Microsoft Graph credential of the owner's own Digiverse identity in one 0600 file read by exactly one program, the model to run as a pure function with no tools while it reads attacker-writable mail and documents, every Draft's recipient fixed by the script and never by the model, every send, move or delete executed only for a proposal the owner approved on a terminal, every memory line validated against a grammar, a length cap, the secret patterns and the minimisation rules before it is written, and every run bounded by a cost cap, a turn cap and a hard stop,
**So that** an injected mail or document can corrupt at most the text and the proposals the owner reads before approving, the credential can never be exfiltrated by a tool call, nothing leaves or moves in the mailbox without a human decision, and a run that fails leaves nothing half-done.

**As** the owner maintaining the template,
**I want** the skill, scripts, prompts, schemas, rules and tests generic in `zyggy-core` and every Digiverse fact (tenant id, client id, mailbox, named sites, exclusions, caps, timer) only in my instance,
**So that** a template change reaches Central with a fast-forward pull and another owner can connect their own tenant from the same template.

Consent-verb gate (shared code in `m365-lib.sh`, `zy_m365_consent_gate <date> <id> <verb>`): (1) `ZYGGY_HOOKS` must not be `off` (exit 5 `refused: consent actions never run unattended`); (2) the proposals file must be a regular 0600 file owned by the caller under the state dir (exit 3); (3) the row must exist (exit 4), be `approved` (exit 5 `refused: proposal #<id> is <status>`), match the verb (exit 5) and carry `decided_at` and `decided_via: tty` written by `m365-approve.sh`; (4) the row is set to `done`/`failed` and the file rewritten atomically **before** the summary line, so a crash leaves at worst an `approved` row that the next approve run shows again as "approved earlier, not executed — run again? [y/N]". The verbs are never called by `brief.sh` or the backfills (AC-33, AC-37, AC-39 assert no such request).

Common behaviour: sequential requests; `Retry-After` honoured on 429/503 (≤ 5 retries, test-only `ZYGGY_RETRY_SCALE`); one silent refresh on 401 then retry once; `curl --proto =https --tlsv1.2 --fail-with-body --silent --show-error --max-time 120 -H 'Accept: application/json'`; never `-v`, never `--trace`; error bodies passed through `zy_secret_match` before being shown; the environment of every `curl` child is `env -i PATH=/usr/bin:/bin HOME=<work tmp> LC_ALL=C` (32 pattern — no proxy, trace or TLS-weakening variable inherited); exit codes `0` done · `3` configuration (env, config, credential file, tools) · `4` usage · `5` refused by policy (`auth` unattended; a Draft already exists; size cap) · `6` Graph/identity failure (auth, HTTP, 410, timeout). stderr lines are prefixed `m365: `, never contain a token, a body or a file content.

## Behaviors & Conventions

- **One credential, one reader.** Only `graph.sh` opens `~/.config/zyggy/m365-refresh-token`; it checks the file (regular, 0600, owner, non-empty) before every refresh (31 checks verbatim) and rewrites it atomically after. The orchestrators never see a token. Override: none.
- **Model as a pure function.** Every model call is `claude -p` with no tools, no MCP, one turn, a budget cap, a JSON schema, hooks off and no session file; its stdin is the fenced batch; its output is validated twice (Claude Code's schema check, then `jq`) before any side effect. Override: none (the flags are constants in `m365-lib.sh`).
- **Fixed write verbs.** Unattended, the mailbox is changed only by `draft-brief` (to the configured mailbox) and `draft-reply` (`createReply` + `PATCH` body/categories of the draft just created). Attended and consented, by exactly three more: `send-draft` (a reply Draft of a run), `move-message` (to a folder of the owner's list), `trash-message` (to Deleted Items). Nothing on the drives is ever written. Override: `actions.allowed` can only narrow.
- **Consent (D6).** A proposal is data: `brief.sh` writes it `pending` and executes nothing. It becomes an action only through `m365-approve.sh`, which (1) needs a tty and refuses `ZYGGY_HOOKS=off`, (2) shows the owner the exact action — for a `send` the Draft's **current** recipients and subject, re-read from Graph, for a `move`/`delete` the subject, sender and destination — and (3) records the owner's `y` with `decided_via: tty` before calling the consent verb, which re-checks the status itself. No other code path writes `approved`. The Claude Code session can list proposals (`/m365 actions`) and nothing more; a request to approve in a conversation is answered with the runbook entry. Override: none.
- **Write bounding (eight layers).** (1) the model has no tool; (2) `graph.sh` implements no send-new/forward/reply-all/permanent-delete/flag/upload verb (exit 4) and its three consent verbs refuse any proposal that is not `approved` for that very verb (exit 5); (3) `PATCH` is accepted only for a draft id in the current run's receipt, `send-draft` only for a draft id in a proposal (created by `createReply`, recipients set by Graph, `bcc` must be empty), `move-message` only to a folder id `brief.sh` resolved from the owner's folder list, `trash-message` only to `deleteditems`; (4) reply and brief bodies are validated (no URL, no address, no secret, length) — a reply failing validation is refused and counted, never patched, and cannot be proposed for sending; (5) `approved` is written only by `m365-approve.sh` after a `/dev/tty` answer; (6) the credential file is unreadable by the model's tools (deny rule), the proposals file is `Edit`-denied, and the unit cannot reach the GitHub token, the clone cache or `~/.ssh`; (7) a proposal expires after `actions.ttl_days`; (8) the mailbox audit log and folder counts prove that every send, move and soft delete by the app matches one `actions.jsonl` line and that the run windows hold none (AC-8, AC-21). Override: none.
- **Injection bounding.** Bodies arrive as plain text (`Prefer` header), cut at `body_cap_bytes`, control characters removed, secret-shaped lines withheld (`zy_secret_match` per line) before the model; one item per fence with a per-run random fence suffix; the prompt states the data rule; no link is ever followed (no tools); generated text may not contain URLs or addresses; recipients are fixed by the script. Documents go through the same path after MarkItDown (text only). Override: none.
- **Idempotence.** One brief per date (receipt + Drafts subject check); a reply Draft at most once per message id; delta links and checkpoints advance only after the side effects they describe; a failed run leaves the previous state intact and the next run redoes the window. Override: none.
- **Caps.** Every model call carries `--max-budget-usd` and `--max-turns 1`; the backfills sum `total_cost_usd` into their checkpoint and stop at `budget_usd_total` or `max_facts` with exit 5; every item has a byte cap; the brief reads at most `mail_max_items` and `files_max_items`. Override: `instance/m365.json`.
- **Facts only.** Memory receives validated `[observed]` lines in `inbox/` through `lib.sh`; nothing else is written under `memory/`; never a body, quote, content, path beyond the source tag, contact detail or third-party detail beyond name/role/organisation. Override: none.
- **Parse and discard.** Downloaded files live in a 0700 temp dir inside the unit's private `/tmp` (or `mktemp -d` for the backfills) and are removed by the trap after each batch; MarkItDown runs under `timeout 120` and `ulimit -v 2097152`; a parse failure is a skip. Override: none.
- **Attended vs unattended.** `brief.sh` is unattended by design (D2, `ZYGGY_HOOKS=off` accepted; the first run is owner-watched before the timer is enabled); `graph.sh auth`, `mail-backfill.sh`, `files-backfill.sh` are owner-started (`ZYGGY_HOOKS=off` → exit 5) and may run unwatched because their model calls are tool-less; `m365-approve.sh` and the consent verbs are **attended only** (tty required, `ZYGGY_HOOKS=off` → exit 5) and involve no model call at all. Override: none.
- **Logging once per run.** One journal/stdout summary line per run and one `brief.jsonl` line; stderr lines only for refusals and errors; no content, no token, no file name of a document beyond the brief itself. Override: none.
- **Throttling.** Sequential, `Retry-After` honoured, ≤ 5 retries, exit 6. Override: none.
- **Data protection (O34, pending the owner's answer).** Unattended runs produce no transcript (`--no-session-persistence`); interactive transcripts follow Claude Code's `cleanupPeriodDays` (the runbook sets it for `zyggy` and records it); memory holds facts only, minimised; a third-party fact is removed on request by deleting the line (28's consolidation then drops it) — git history of the memory repository keeps the deleted line until the owner rewrites history (runbook entry "Erase a fact from history": `git filter-repo` on the private memory repository, or accept the retention); the model provider sees the fenced batches under the owner's subscription terms (OQ-5). Override: the owner's decision in OQ-5.
- **Template/instance.** The template names no tenant, mailbox, site, client id, cap value beyond defaults or machine path; every Digiverse fact lives in `instance/m365.json`, `instance/systemd/*` and `instance.md`. Override: none.

## Deliberate deviations from the founding spec and the hand-off brief

- **No MCP server and no `.mcp.json` entry** (founding §3 "Gmail/Outlook.com MCP over Microsoft Graph"; brief scope item (b) "MCP server(s) … in `.mcp.json`") — a script-driven Graph client with a tool-less model gives a strictly smaller attack surface and less owned configuration; no verified candidate fits a consent-gated work-account deployment (OQ-3; founding wording in OQ-4).
- **Send, move and delete exist, gated by per-action consent (D6)** — against the roadmap brief's D1 "Drafts only, the owner sends in Outlook" and the founding §1 non-goal "no automatic sending": nothing is automatic — the unattended run proposes, the owner approves each action on a terminal, and only then does a script act. `Mail.Send` is granted for that one verb. Recorded in 0002 as a deviation row with the date of the owner's decision.
- **No device-code flow** (brief Q2 option; founding §8 "device-code delegated auth (preferred)" was written for the work laptop) — blocked by security defaults and discouraged by Microsoft; the auth-code + PKCE bootstrap in the laptop browser replaces it (OQ-2).
- **No `LoadCredential=`** (brief scope (a), 31 Finding 3 "when a unit is involved") — the refresh token rotates on every run; the unit gets the one file read-write instead; `LoadCredential=` remains the right channel for a static secret (the app-only fallback's PEM).
- **`InaccessiblePaths=` per file, not the whole `~/.config/zyggy`** (32 Finding 1) — the Graph credential must be reachable; the GitHub token file and the clone cache stay inaccessible.
- **`triage-mail` → `m365`** (founding §3 Skills) and the Central row of that table describe scripts run by a timer, not a model-driven skill (OQ-4 wording).
- **The founding spec's §8 Secrets row "Gmail / Outlook.com OAuth refresh tokens — Central: systemd credential; MCP server reads at start"** becomes the Microsoft Graph refresh-token row above (OQ-4).
- **Three unattended/unwatched credentialed runs before 18–20** (27/31 attended-only rule): the brief (owner decision D2), the recurring file review (D5b), and the owner-started backfills running unwatched (analyst) — bounded by the tool-less model; recorded in 0002.
- **Backfills do not wait for 28** (brief re-split trigger) — `inbox/` is inert until consolidated; no re-split proposed.

## Edge Cases

| Case | Expected behavior |
|------|-------------------|
| The VM was down at 06:30 | `Persistent=true` runs the brief at boot for that date; the window covers the missed period (delta). |
| Two briefs on one date (manual + timer) | Second = `already created`. |
| A mail with no body (meeting invite, empty) | Listed with its subject; summary "(no text)". |
| A mail in a language other than English | Summarised in the owner's conversational language (prompt rule: the brief is written in `preferences.md`'s language — the script passes the configured language from `instance/m365.json` `brief.language` default `en`). |
| `replyTo` set on the original | `createReply` targets it (Graph behaviour); the brief shows the recipient Graph chose. |
| A reply proposed for a mail the owner sent himself (Sent Items never read by the brief; a self-addressed Inbox mail) | Recipient = the owner; harmless. |
| More than `mail_max_items` new mails | The newest `mail_max_items` are summarised; the brief says "and <k> more, not summarised"; the delta link still advances (unsummarised mails are not re-read — the owner reads them in Outlook). *Analyst decision; veto.* |
| A changed file the owner cannot download (403 on a site) | Skipped with reason `forbidden`, listed by name. |
| A OneDrive shared-with-me item | Not in `/me/drive` delta (own drive only) — out of scope. |
| A site in `sites` that does not exist / no access | `check` and the backfill exit 3 naming the site. |
| A 0-byte or binary-mislabelled `.docx` | MarkItDown fails → skip + count. |
| A fact line equal to one already in the file | Dropped (exact match only; 28 handles paraphrases). |
| The owner's own name/address in a fact | Allowed for the name; the address is refused by the validator like any address (the fact "the owner's address is X" is not needed — memory already knows). |
| The same message appears twice in a delta page | Processed once per id (set in the batch). |
| The brief's `claude` call returns zero items/replies/facts | Draft still created ("No actionable mail"); counts zero. |
| The owner edits a reply Draft in Outlook, then approves `#<id> send` | The Draft as edited is sent (Graph sends the stored draft); `m365-approve.sh` showed the current recipients/subject before asking. |
| The owner sends a reply Draft in Outlook himself, then runs `m365-approve.sh` | The `send` proposal shows `already sent`, is closed as `done` (`sent earlier`) without a request. |
| The owner moves or deletes a mail in Outlook before approving its `move`/`delete` | 404 → row `failed: message gone`; nothing else touched. |
| Two `move` proposals for the same message (two runs, same window after a failed day) | The second run skips a message id that already has a `pending`/`approved` proposal (receipt-style dedupe across the TTL window). |
| The model proposes `delete` for a mail the owner sent himself, or `move` to Drafts/Sent Items/Deleted Items/Junk | Refused by `brief.sh`: `move` destinations exclude well-known system folders (`drafts`, `sentitems`, `deleteditems`, `junkemail`, `outbox`); `delete` of a Sent Items mail is impossible (Sent Items is never in the brief's batch). |
| `actions.allowed` is `[]` | No menu in the prompt, `actions[]` ignored if present, section reads "none (proposals disabled)", `m365-approve.sh --list` prints "proposals disabled". |
