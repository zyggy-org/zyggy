# Zyggy.Cli

The `zyggy` command-line tool, published as a single-file binary and placed on the PATH of every machine. It is how Claude Code skills and the user interact with the bus and the node without touching git or envelope formats by hand.

## Verbs

| Verb | Used by | What it does |
|------|---------|--------------|
| `submit --to <machine> --project <path|name> [--agent <name>] [--timeout <minutes>] [--allowed-tools <a,b>]… [--priority low|normal|high] [--worktree [--branch <name>]] [--description <text>] [<body>]` | Central's `delegate` skill, the user | Build, sign and publish a job envelope into `nodes/<machine>/jobs/` (deliverable 08). The body is the last argument or standard input. `--worktree` (deliverable 16) sets `worktree: true`: the target runs the job in its own git worktree on branch `zyggy/<id>`, commits what the model left, pushes the branch to the project's `origin` and reports the pushed SHA as `diff_ref` and the changed paths as `files_changed`; without it the job runs in the project's checkout and never commits. `--branch <name>` (deliverable 53, only with `--worktree`) sets `branch`: the job still runs on `zyggy/<id>`, started at `origin/<name>` when that exists (else the default tip), and a `done` run is pushed to `<name>` on `origin` without force, so the branch is only created or fast-forwarded; a `failed` or `timeout` run, a refused push or a project without `origin` leaves the named branch unchanged and the work on `zyggy/<id>` (Core README, "Jobs: named branch not changed"); a local branch of that name is never read or written. `--description <text>` (with or without `--branch`) sets `description`, one line of 1–200 characters: the node's commit subject (body `zyggy job <id>`) and a `description:` report line, never shown to the model. Before signing, `--branch` is refused without `--worktree`, when it breaks the name rule (Core README, "Jobs: branch name refused"), or when it equals the target project's `default_branch` in the target machine's registry file in the bus checkout, in any letter case (skipped when that file is absent, unreadable or foreign, or the project has no entry by name; the node checks again in every case); `zyggy: branch: <detail>` / `zyggy: description: <detail>`, exit 2, nothing written. Every option is checked by shape before anything is signed (`to`/`project`/`agent`/`timeout_minutes`/`allowed_tools[i]`/`priority`/`body`; limits: project 1024, agent 64, tool item 128 characters, timeout 1–1440 min, body 64 KiB); the signed bytes are parsed and verified again before they are written. Prints `submitted <id> to <machine> (<path>)`. Exit 0; 7 committed locally but not pushed (the next bus write pushes it); 2 an option refused (`zyggy: <field>: <detail>`) or the self-check refused; 3 configuration (`node.json`, `signWith` missing, checkout not a repository / wrong branch / no `tenants/<tenant>/`); 6 the signing key is not in the store (the hint names `zyggy secret set`), the checkout busy, or the write failed at `pull`/`add`/`commit` (working copy restored). |

## Rules

- Built on System.CommandLine, one file per verb.
- All behaviour comes from `Zyggy.Core`: the CLI parses arguments, calls the library, prints results, and returns a non-zero exit code with a one-line error on failure.
- Never handles credentials itself; signing keys come from `ISecretStore`, git authentication is git's concern.

Founding spec: §3 (component table), §11 (status and costs), §14 (init, diagnose).

## node.json (minimal, deliverable 04)

Every bus verb reads `node.json`: `--config <path>`, else `ZYGGY_NODE_JSON`, else `%LOCALAPPDATA%\zyggy\node.json` on Windows and `~/.config/zyggy/node.json` on Linux.

```json
{
  "tenant": "<tenant>",
  "machine": "<machine>",
  "signWith": "<tenant>/1",
  "bus": {
    "owner": "zyggy-org",
    "repo": "zyggy-bus",
    "branch": "main",
    "localPath": "C:/agents/bus",
    "remote": "https://github.com/zyggy-org/zyggy-bus.git"
  },
  "poll": { "activeSeconds": 10, "idleSeconds": 60 },
  "secrets": { "store": "os", "root": null }
}
```

## Per-machine setup

The bus repository `zyggy-org/zyggy-bus` is created by hand (spec 04 AC-36): private, a ruleset on `main` blocking force-push and deletion, a `PROTOCOL.md` placeholder, `tenants/<tenant>/nodes/<machine>/{jobs,jobs/claimed,jobs/rejected,reports,context}` and `tenants/<tenant>/registry` with `.gitkeep` files, **and a `.gitattributes` with `* -text`** so no checkout ever rewrites an envelope's line endings. One fine-grained token per machine, scoped to that one repository.

**Central (Linux, user `zyggy`)**

1. `ssh-keygen -t ed25519 -f ~/.ssh/zyggy_zyggy-bus_ed25519 -N ''`; add the public key as a write deploy key; in `~/.ssh/config`: `Host github.com-zyggy-bus` → `HostName github.com`, `IdentityFile ~/.ssh/zyggy_zyggy-bus_ed25519`, `IdentitiesOnly yes`.
2. `git clone git@github.com-zyggy-bus:zyggy-org/zyggy-bus.git <bus.localPath>`.
3. `zyggy secret set hmac/1 --generate --show` once for the tenant (the hex line is shown once: carry it to the other machines over a channel you trust, never a repository or chat log), then `zyggy secret set github-pat` (the hidden prompt: paste the token, Enter) — the token is for the API head check only (Contents read). Both land as 0600 files under `~/.local/share/zyggy/secrets/<tenant>/`; the unit reads the same files; the optional credentials drop-in is in `install-node.md`. `zyggy secret list` shows what the machine holds and the fingerprints to compare.
4. `zyggy probe reach`, then install the unit per `zyggy-core/runbooks/install-node.md` (`deploy/systemd/zyggy-node.service` from the release); `zyggy status` → `health: green`.

**Laptops (Windows)**

1. Install Git for Windows (Git Credential Manager is its default helper). Then, after steps 2 and 3, run `install.ps1 -Tenant <org> -Machine <name> -SignWith <org>/<n>` from the release folder in a plain PowerShell (no administrator): it checks the checksums, copies the binaries to `%LOCALAPPDATA%\Programs\Zyggy`, adds them to your PATH, writes `node.json` when absent, runs `zyggy setup` (deliverable 42: completes `node.json`, clones or updates `zyggy-core`, wires the user-scope Claude Code settings and skills, names every missing secret with the command that sets it) and registers the per-user logon task `zyggy-node` (procedure: `zyggy-core/runbooks/install-node.md`).
2. `git clone https://github.com/zyggy-org/zyggy-bus.git <bus.localPath>`; `git -C <bus.localPath> config core.autocrlf false` until the repository's `.gitattributes` is in place.
3. Windows: the Credential Manager is the store — nothing to install. `zyggy secret set hmac/1 --hex` (paste Central's hex at the hidden prompt; `zyggy secret list` must show the same fingerprint as on Central) and `zyggy secret set github-pat` (this laptop's fine-grained token, Contents read and write). Both appear in Control Panel → Credential Manager → Windows Credentials as `zyggy/<tenant>/<name>`, for this Windows user only. Git authenticates itself (Git Credential Manager); the stored token serves the API poll only.
4. `zyggy probe reach`: the `push` check (`git push --dry-run`) makes Git Credential Manager ask for the token once and store it in the Windows Credential Manager.
5. **One documented git settings pass**, only if `reach` fails on the work laptop, as the owner's own settings (Zyggy never writes `git config`): `git config --global http.proxy http://<host>:<port>`, `git config --global http.sslBackend schannel` (trust the corporate root CA from the Windows store), `git config --global credential.helper manager`. Run `reach` again; a check that still fails goes into the transport decision record, not into more tweaking.

## Troubleshooting — Setup

Fix what the row says, then run `install.ps1` again with the same parameters: what is already in place prints `already done`. | Probe: git through the proxy — `fetch`/`push` `unreachable` or `tls failed` while `api` is `ok` | git does not read `HTTPS_PROXY` the same way: run the settings pass above once, then `reach` again. |
| Probe: no report — `send` prints `timeout` | Is `listen` running on the target, and what does its stderr say? Run `reach` on the target. A `rejected <reason>` line instead means the target refused the job: see the Core README "Bus: rejected envelopes". An `unverified_report` outcome means the target answered but its report did not verify (`unknown_key`: the sender does not hold the key the target signs with; `invalid_signature`: the bytes changed on the way): the fix is the keys row above: the same `hmac/1` hex on both machines. |
| Probe: `push_failed pull: …` from `send` | The sender's own checkout is dirty or behind; `send` does not stash (only `listen` does): `git -C <bus.localPath> status`, then `git stash` or `git checkout -- .`. |
| `node.json` — exit 3 `zyggy: configuration error: <key>: <detail>` | The key named is missing or invalid; `secrets never in node.json` means a key looked like a credential; `secrets.store: one of os, file` names the store words. The schema is above. |

## Troubleshooting — Secrets

| Situation | What to do |
|-----------|------------|
| Secrets: entering a value — `secret set` exits 2 with one line | A value as an argument has no form: pipe it (`Get-Content key.txt \| zyggy secret set hmac/1 --hex`), or run the verb at a terminal and type it blind at the hidden prompt. `--hex` expects hexadecimal text; the cap is 512 bytes; `--generate` is for `hmac/<n>` only and takes no input; `--show` needs `--generate`. Exit 5 means the prompt was aborted; nothing was stored. |
| Secrets: store unavailable (Windows) — `secret store unavailable: credential-manager: 1312 …` (exit 6) or the node's `refusing to start: secret store unavailable: …` | The Credential Manager is per Windows user and per logon session; the node runs as a scheduled task inside your own logon session (deliverable 10's `install.ps1`), the same session `zyggy secret set` used — a 1312 under the task is a finding to report, not an expected state. |
| Secrets: file store on Windows — the warning `file secret store selected on Windows: spike and test use only; the product store is Credential Manager` on every run | Allowed for tests and spikes. For a real machine remove `"store": "file"` from `node.json` and move the keys into the Credential Manager per the "First execution — retire the spike file store" paragraph of the Core README's `rotate-hmac.md` draft. `zyggy setup` names a spike store it finds with the line `setup: spike file store: left as is - …` (see "Troubleshooting — Setup"). |
| Secrets: corrupt value — `secret store unavailable: corrupt value: …` or `Credential '…' does not hold a hexadecimal value` | A value was written by hand or by another tool. Re-enter it with `zyggy secret set <name> --hex`; the message names the target or the path, never the content. |
| Secrets: rotation — a key replaced, leaked or to be retired; `secret remove hmac/<n>` refused (exit 2) | Follow the `rotate-hmac.md` draft in the Core README: a new key signs, the old one stays verify-only; `secret remove` of the `signWith` key is refused until `signWith` names the new key. A replaced `hmac/<n>` on one machine only breaks verification tenant-wide: compare fingerprints with `zyggy secret list`. |

## Troubleshooting — Submit / Status / Verify

| Situation | What to do |
|-----------|------------|
| Submit: `zyggy: <field>: <detail>` (exit 2) | An option is refused by shape before anything is signed: `to` a lowercase label; `project` a registry name (`[a-z0-9-]`) or an absolute path (POSIX or Windows), ≤ 1024 characters, no `..`; `agent` 1–64 of `A–Z a–z 0–9 . _ -`; `timeout_minutes` 1–1440; `allowed_tools[i]` no empty item (a double comma), ≤ 128 characters; `priority` `low`, `normal` or `high` (case-sensitive); `body` not blank, ≤ 64 KiB; `branch` only with `--worktree`, the §4 name rule, and not the target project's registry `default_branch` in any letter case; `description` one line of 1–200 characters. Fix the option named (the Core README's "Jobs: branch name refused" row has the name rule). |
| Submit: `refusing to submit: the envelope does not round-trip (<field>)` (exit 2) | The signed bytes did not read back as the request — a bug in the writer, never a user error. Nothing was written. Report it with the field named. |
| Submit: `signing key <tenant>/<n> is not in the <store>; run: zyggy secret set hmac/<n> --hex` (exit 6) | The "Bus: keys" row above: enter the tenant's key on this machine at the hidden prompt and compare fingerprints with `zyggy secret list`. |
| Submit / status / verify / probe: `zyggy: secret store unavailable: <store>: <detail>` (exit 6) | The "Secrets: store unavailable (Windows)" or "Secrets: corrupt value" row above; nothing was written. |
| Submit: `submit failed at pull: …` (exit 6) | The sender's checkout could not be brought up to date (remote unreachable, authentication, a conflicting local change). Nothing was written; the working copy is as it was. `zyggy probe reach`, then `git -C <bus.localPath> status`. |
| Submit / status / verify: `the bus checkout is busy: another zyggy process held its lock` (exit 3 or 6) | Another `zyggy` command or the node held the checkout's write lock for the whole 60 s wait. Wait and retry; if it persists, a stale `.git/zyggy-bus.lock` from a killed process can be deleted once nothing else runs. |
| Submit: `submitted … (committed locally, not yet pushed …)` (exit 7) | The push was refused four times. The job is committed in your checkout and goes out with the next bus write from this machine (a `submit`, or the node's next claim or report). Nothing to undo. |
| Status: `health: down — no node service answering on http://localhost:4711/health` (exit 6) | The node service is not running on this machine (or binds another port, which deliverable 07 does not allow). Start the service; the bus block below is still complete. |
| Status: `health: red — …` (exit 6) | `claude not logged in`: run `claude login` as the service user. `not polling: last poll <age>` / `never polled`: the service is wedged or just started — its log under `<nodeDir>/logs/`. |
| Status: `health: amber — …` (exit 1) | Look later: `backing off until …` (the bus host rate-limited the node), `claude auth not yet probed` (just started), `rate limit low: <n>`, `never pulled`, `node <v>, cli <v>` (upgrade one of them). |
| Status: `not found in tenant <tenant>` (exit 1) | No file on the bus names that id: never submitted here, or already archived beyond what the bus still holds. |
| Verify: `FAIL … invalid_signature (sig)` / `tenant_mismatch (tenant)` / `id_differs (id)` / `type_folder_mismatch (type)` / `writer_mismatch (from|to)` | Drift: a file was edited after signing, written by hand, or moved by hand. The ledger is append-only: investigate with `git -C <bus.localPath> log -p -- <path>`; a hand-edited file is restored from history, never re-signed. |
| Verify: `FAIL … unknown_key (<tenant>/<n>)` | The file was signed with a key this machine does not hold — after a rotation, the retired key (deliverable 09 keeps retired keys verify-only); otherwise a foreign writer. |
| Verify: `WARN tenants/<other>/ second tenant directory …` (exit 6) | §13: one bus repository per tenant. The other directory is never read; remove it from the repository or give that tenant its own. |
| Verify: `FAIL <path> unexpected_path` | A file or folder §4 does not know (a stray folder, a file at the tenant root other than `policy.yaml`). Remove it or move it to a §4 place. |
| Status: the health endpoint answers but not with JSON | `health: down — …` after `unparsable body` or `HTTP <code>`: something else listens on 4711. `netstat`/`ss` for the port. |

## Troubleshooting — Context

| Symptom | What to do |
|---------|------------|
| `zyggy: <field>: <detail>` (exit 2) | The scope or the fact was refused before anything was signed: `--scope` takes `general`, `project:<name>` (lowercase letters, digits, hyphens) or `machine`; the fact is one sentence of at most 1000 characters. `zyggy: to: this machine is central` means the verb ran on Central: there, use `zyggy memory remember`. |
| `zyggy: refused: matches secret pattern <name>` (exit 5) | The fact looks like a secret. Nothing was signed or written. Never retry, never rephrase, never store it another way: keep the secret where it belongs. |
| `zyggy: configuration error: … secret patterns …` or `ZYGGY_SECRET_PATTERNS is not set` (exit 3) | The laptop cannot find `secret-patterns.txt`, so nothing is sent (fail closed). Set `ZYGGY_SECRET_PATTERNS` to `<zyggy-core>/.claude/hooks/secret-patterns.txt` in the user-scope `~/.claude/settings.json` `env` (`install.ps1` (`zyggy setup`) sets it). Still exit 3 after a clean `setup`: check `/status` in Claude Code for managed (enterprise) settings, which outrank the user settings; `setup` never writes managed files. |
| `zyggy: the bus checkout is busy: another zyggy process held its lock` (exit 6) | Another `zyggy` process is writing to the same checkout. Run the command again; a spool stays where it is until a flush succeeds. |
| `zyggy: context failed at pull: …` (exit 6) | The checkout could not be brought up to date (offline, authentication, a conflicting local change). Nothing was written; a spool is kept for the next flush. `zyggy probe reach`, then `git -C <bus.localPath> status`. |
| `… (committed locally, not yet pushed: …)` (exit 7) | The envelope is committed in the checkout; the next bus write on this machine pushes it. When it keeps happening, follow `bus-conflict.md`. |
| `context: cap of 150 hook lines reached for session <id8>` | A very long session: the spool holds 150 turn notes and a `cap reached` marker; later turns are not noted. Nothing to do; the spool ships at session end. |
| Context or item not sent — `zyggy: context failed at <stage>: …` / `zyggy: item failed at <stage>: …` (exit 6) or `… (committed locally, not yet pushed: …)` (exit 7) from `zyggy context` or `zyggy archive` | Exit 6: nothing was published — `zyggy probe reach`, then `git -C <bus.localPath> status`; the key and store lines name `zyggy secret set`. Exit 7: the envelope is committed and goes out with the next bus write on this machine. For a OneDrive-route item whose file was already written, re-run the **same** `zyggy archive` call once the bus is reachable: the identical file is found and exactly one envelope is published. (Not for the OneDrive-folder lines: see "Troubleshooting — Archive from a laptop".) |
| A spool left behind under `<nodeDir>/context/<tenant>/` | A session crashed or the flush failed. The next session end ships every spool older than an hour; to ship them now, run `zyggy context --flush` by hand. `command not found` from a launcher: the `zyggy` binary is missing from the user `PATH` or too old — reinstall per `install-node.md`, section "Laptop". |

## Troubleshooting — Work, ask and decide

| Symptom | What to do |
|---------|------------|
| Refused text — `zyggy: refused: <field>: matches secret pattern <name>` (exit 5) from `zyggy ask`, `zyggy decide` or `zyggy work --step`, or one stderr line `work: status refused (…)` from a hook | The question, option, default, decision text, undo line, step or a status value looks like a secret, or is over its size limit (`breaks its rule`: question 600, decision 1200, a line 200 characters). Nothing was signed or written, and the text is kept nowhere. Never retry with the same text, never rephrase a secret to get it through; ask without it. |
| No status from a laptop — `zyggy work` on Central shows no session for a laptop that has one, or shows it `silent` | The session's hooks did not reach the bus. On the laptop: are the three hook lines wired (`zyggy-core/node/README.md`, "Wiring"), is `supervision.enabled` true, does `zyggy probe reach` pass? A hook that failed printed one line per streak (`work: status not published (…)`) and tries again at the next turn end; nothing is queued. `silent` alone means the status file is over 60 minutes old: the session has not ended a turn since, or it crashed (its file is removed by that machine's next status write after 24 hours). Central's own checkout is as fresh as its node's last pull. |
| `zyggy: ask: no live session of this project on this machine, and no job run` (exit 2) | `zyggy ask` names its asker from the session-start hook's local state. Run it from the project's folder, in a session whose hooks are wired; in a job run the node sets `ZYGGY_JOB`. |
| `no answer; default: <default>` (exit 8) | Central did not decide within the wait. Follow the default and say so in the reply or report. The question stays open on the bus; a decision that comes later is printed once at the next session start in that project and is listed by `zyggy decisions`. With `zyggy: the question has not left this machine yet` on stderr, the commit is local: the next bus write pushes it. |
| `zyggy: refused: only central decides` (exit 3) | `zyggy decide` ran on a laptop. Only the machine named `central` writes decisions; a decision from any other sender does not parse. |
| `zyggy: decide: nothing on the bus has that id` (exit 1) | `--reply-to` names no question, job or report in Central's checkout, or the file there does not verify. `zyggy work` lists the open questions; `zyggy verify` names a file that fails. |
| `zyggy verify` reports `nodes/<machine>/status/…`, `questions/…` or `decisions/…` as `unexpected_path` | That machine's `zyggy` is older than deliverable 18. Upgrade it; the files are valid. |

## Troubleshooting — Mandate and supervisor

| Symptom | What to do |
|---------|------------|
| Mandate refused — `zyggy: refused: mandate <limit>: <detail>` (exit 3) from `zyggy submit --mandate`, or a job rejected `mandate_invalid` with the node log line `job <id> refused under mandate <id>: <limit>` | The submit or the job is outside what the owner granted. The limit is named: `absent`, `unverified`, `revoked`, `expired`, `paused`, `max_jobs`, `machine`, `project`, `allowed_tools`, `branches`, `max_jobs_per_hour`, `max_jobs_per_step`, `grants`, `sessions`, `usage_limit`, `work_machine`, `capability`, `worktree`, and on the node `supervision_stopped` (the owner ran `zyggy supervise stop` there; `zyggy supervise start` lifts it). `zyggy mandate show` prints the mandate's state and what is used. Nothing was written (a rejected job sits in `jobs/rejected/` with its report). Never widen a job to get it through: the owner grants a new mandate, or the work waits. A node whose `supervision.enabled` is `false` refuses every job under a mandate. |
| Mandate paused — `zyggy mandate show` reads `paused`, and Central's node wrote an `escalate` decision on the third failing report | Its three newest reports are all not `done` (failed, timeout or rejected). Read them with `zyggy report <id>`; the decision's evidence names them. When the cause is fixed, the owner runs `zyggy mandate resume <id>` in a conversation on Central; the reports before it no longer count. A step at its cap does not pause the mandate: submits for that step are refused and the supervisor escalates. |
| Usage limit — `zyggy: refused: mandate usage_limit: …` | The newest report under the mandate is a usage limit of the model (`claude_error: rate_limit`) less than 60 minutes old. No job is submitted under that mandate until the hour has passed; nothing to do but wait, or revoke. |
| Supervisor could not decide — a decision of kind `escalate` with the text `supervisor could not decide: 2 runs ended without a decision (blocked calls: <n>)` | Two supervisor runs on that report or question ended without `zyggy decide`. The node log has one line per run, `supervisor run on <id> attempt <n> ended: <outcome>, blocked: <n>`; the transcript and the blocked-calls file are under `<nodeDir>/runs/<tenant>/<id>.jsonl` and `.blocked`. Decide it yourself with `zyggy decide --reply-to <id> …`. A blocked count above zero means the run tried a tool outside its fixed list, or a read outside its read root. |
| Supervisor does not start — a report or question stays without a decision, and the node log has `supervisor: no run starts, supervision.project is not set` or `… is not a project of this machine` | On Central, in a conversation, the `settings` skill: `zyggy settings set supervision.project <name>` with the registry name of Central's own project (`zyggy registry --machine central` lists the names; `zyggy settings show` what is set). When the project is not published, first `zyggy settings add devRoots <parent> --exclude <home folder name>`. The node applies both within a minute, no restart. `supervisor: hourly cap of <n> run(s) reached` means `supervision.runsPerHour` runs started within the hour: the event waits. `supervisor: failed at <stage>: <detail>` names a write the node could not make; it is logged once per streak and tried again at the next pass. With `supervision.enabled: false` nothing wakes. |
| Upgrade before a mandate — `zyggy: refused: mandate capability: …` | The target's registry file does not list the capability `supervision`: its node is older than deliverable 18 and would not copy `mandate` and `step` into its reports, so its jobs could not be counted. Upgrade that machine (`install-node.md`), let it publish its registry (`zyggy registry --machine <name>`), then submit again. |
| Branch moved under a job — a `done` report with the line `branch <base> not updated (moved meanwhile); the result is zyggy/<id>` | The mandate's branch moved on the remote while the job ran (the owner pushed, or another job). Nothing was forced: the job's commits are on `zyggy/<id>`. Merge or rebase that branch by hand, or let the next job start from the moved branch. `branch <base> not updated: default branch` means the job named the project's default branch, which a node never pushes. |
| No mail from Central — an item is on `zyggy work --waiting` but no mail came; Central's node log has `owner mail: send failed, tried again in a minute: <detail>` (Error, once per streak) | The mail goes out through Graph from the owner's mailbox to itself, at most once per 30 minutes, naming only items no earlier mail named. `owner mail not configured: …` — the node has no M365 instance (`ZYGGY_INSTANCE_DIR`, `m365.json`, the Graph key); `owner mail not sent (403)` — the app registration lacks `Mail.Send` on that mailbox; `no token` — the key or certificate (runbook 13). The node keeps running and tries again every minute; the list and the brief's "Decided for you" show the items meanwhile. What a mail named is kept in `<nodeDir>/owner-mail.json`; deleting it means one more mail. |
| Supervision stopped — Central's log has `supervisor: stopped by the owner; no run starts until zyggy supervise start`, or a laptop rejects mandate jobs with limit `supervision_stopped` | The owner ran `zyggy supervise stop` on that machine: the file `supervision-stopped` is in its node folder. `zyggy supervise start` in an attended session removes it; mandates revoked by the stop stay revoked, the owner grants new ones. |
